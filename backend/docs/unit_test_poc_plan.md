# 단위 테스트 및 대용량 PDF POC 검증 계획

## 1. 목표

본 계획은 작은 페이지 수의 fixture 기반 단위 테스트에서 시작해, 실제 300페이지 이상 스캔 PDF를 처리하는 POC까지 단계적으로 확장한다. 최종 목표는 목표 NPU 노트북에서 메모리 안정성, OCR 정확도, 처리 시간이 실제 운용 기준을 만족함을 증명하는 것이다.

## 2. 검증 계층

| 계층 | 범위 | 입력/엔진 | 실행 시점 |
|---|---|---|---|
| 단위 테스트 | 함수 계약, 예외, 경계 조건 | 1~5페이지 fixture, Fake OCR/LLM | 매 커밋 |
| 통합 테스트 | PDF→OCR→구조화→평가 연결 | 10~30페이지 실제 스캔 PDF | PR/릴리스 전 |
| 확장 검증 | 청크 크기·병목 조정 | 50~100페이지 실제 스캔 PDF | 대용량 POC 전 |
| 대용량 POC | 실제 운용 적합성 입증 | 300페이지 이상, 배포 후보 OCR/LLM | 엔진·성능 변경 및 배포 전 |

POC에서 발견한 결함은 최소 재현 fixture로 축소해 단위 테스트에 추가한다. POC는 기본 `pytest`에서 제외하고 `poc` marker 또는 별도 벤치마크 명령으로 실행한다.

## 3. 단계별 계획

### Phase 0. 공통 계약 및 측정 기반

* `LLMEngineInterface`, `OCREngineInterface`는 ABC로 정의하고 단위 테스트는 Fake 구현체를 사용한다.
* 페이지 데이터는 최소 `page`, `text`, `bbox`, `image_path`(또는 이미지 객체)를 포함한다.
* 모든 테스트는 실행 시간(sec)을 기록한다. PDF 청크/POC는 RSS(MB), 최대 RSS, `gc.collect()` 후 RSS도 기록한다.
* 성능 로그는 JSON/CSV로 저장하며 입력 파일 해시, 엔진 버전, 장비 사양, DPI, 청크 크기, 스레드 수를 함께 남긴다.

### Phase 1. 작은 fixture 단위 테스트 (1~5페이지)

아래 Test 01~07은 실제 Ollama, 실제 대용량 PDF, 네트워크에 의존하지 않고 빠르게 반복 실행한다. 정상·빈 입력·경계·오류 케이스를 포함한다.

| 테스트 | 추가 핵심 검증 |
|---|---|
| Test 01 PDF 청크 | 청크 경계, 페이지 누락/중복 없음, 청크 종료 후 GC 호출 |
| Test 02 블라인드 | whitelist 제외, `bbox`, `PENDING_REVIEW`, 감점 결과 |
| Test 03 B권 증빙 | 목차 `declared_page`, 상단 25% ROI, 제목 탐지, 수동 보정 병합 |
| Test 04 섹션화 | 헤더/목차 분할, 페이지 범위, 헤더 실패 시 fallback |
| Test 05 토큰/LLM | 슬라이딩 윈도우, JSON 및 `score`/`reason`/`evidence` 스키마 |
| Test 06 RAG | 관련 섹션 검색 및 실제 근거 페이지 `citation_pages` |
| Test 07 컴플라이언스 | 법령명, 페이지, 심각도를 포함한 위반 리포트 |

### Phase 2. 소규모 실제 PDF 통합 테스트 (10~30페이지)

텍스트형, 스캔형, 표·도장·헤더/푸터 혼합형 문서를 준비한다. 실제 OCR 후보 엔진으로 PDF 렌더링→OCR→구조화→규칙 평가를 연결하고, 원본과 처리 결과의 페이지 수 일치 및 OCR 오류 페이지의 리포팅을 검증한다. LLM은 고정 응답 엔진으로 시작해 OCR 문제와 생성 문제를 분리한다.

### Phase 3. 중간 규모 확장 검증 (50~100페이지)

`chunk_page_size=30`과 `50`을 각각 실행해 최대 RSS와 페이지당 처리 시간을 비교한다. 저품질/회전/빈 페이지/대형 표를 포함하고, OCR 재시도 뒤에도 페이지 누락·중복이 0건인지 확인한다. B권은 전체 OCR과 상단 25% ROI OCR의 증빙서류 탐지 결과와 시간을 비교한다.

### Phase 4. 300페이지 이상 실제 운용 POC

목표 NPU 노트북 또는 동등한 RAM·CPU 장비에서 배포 후보 OCR/LLM으로 수행한다. 입력은 200~300dpi 수준의 300페이지 이상 스캔 PDF이며 한글/영문, 표, 도장, 저품질 페이지, 헤더/푸터, 목차, 증빙문서를 포함해야 한다. 실제 RFP/A권/B권 형식의 비식별화 문서를 우선 사용하고, 불가능하면 동등한 합성 문서를 사용한다.

정확도 측정을 위해 대표 50~100페이지에 텍스트/핵심 키워드, 증빙 제목·존재 여부, 블라인드 위반 위치, 섹션 페이지의 정답셋을 만든다.

| 설정 | 실행 |
|---|---|
| 청크 크기 | 30페이지와 50페이지 |
| 반복 | 설정별 최소 3회 |
| OCR 방식 | 전체 OCR 및 B권 상단 25% ROI OCR |
| 엔진 | 배포 후보별 실행 및 버전 기록 |

청크별 로그:

```text
run_id, document_hash, engine_version, chunk_no, start_page, end_page,
rss_before_mb, rss_peak_mb, rss_after_gc_mb, chunk_seconds,
render_seconds, ocr_seconds, parse_seconds, evaluate_seconds,
processed_pages, failed_pages, duplicate_pages
```

## 4. POC 판정 기준

정확한 수치는 목표 장비의 RAM과 Tauri UI/OS 점유 예산을 확인한 뒤 확정한다. 확정 전 최소 기준은 다음과 같다.

* 300페이지 처리에서 페이지 누락과 중복이 0건이다.
* 청크별 GC 후 RSS가 청크 수에 비례해 계속 증가하지 않으며, 같은 문서 3회 실행 때 최대/종료 RSS가 누적 상승하지 않는다.
* Python Sidecar 최대 RSS가 목표 장비의 별도 운영 예산 이내다.
* 일반 OCR은 CER/WER 또는 핵심 키워드 재현율을, 증빙서류·블라인드 탐지는 Precision/Recall/F1을 정답셋으로 측정한다. 블라인드는 Recall을 우선한다.
* 섹션 시작/종료 페이지 일치율, LLM JSON 유효성(100%), 인용 페이지 일치율을 측정한다.
* ROI OCR은 전체 OCR 대비 증빙서류 Recall 저하와 처리 시간 절감률을 함께 비교한다.
* 렌더링, OCR, 구조화, 정량 평가, 검색/RAG, LLM 평가 시간을 분리하고 평균 및 p95 페이지 처리 시간을 보고한다.

## 5. 실행 및 산출물

```bash
pytest tests/                       # 빠른 단위 테스트
pytest -m integration tests/        # 10~30페이지 통합 테스트
pytest -m poc tests/ --poc-pdf /path/to/representative-300-pages.pdf
```

POC 원본 PDF는 저장소에 커밋하지 않고 접근 제어된 경로에 보관하며, 결과에는 문서 해시와 메타데이터만 남긴다.

산출물은 실행 요약(통과/실패, 설정, 총 시간, 최대 RSS, 오류 수), 청크별 메모리·시간 CSV/그래프, 정확도 리포트, 전체 OCR 대 ROI OCR 비교표, 실패 페이지 및 이를 재현하는 신규 단위 테스트 목록으로 구성한다.

## 6. 완료 조건

1. Test 01~07이 독립적으로 통과한다.
2. 10~30페이지 통합 테스트에서 실제 OCR 파이프라인의 페이지 누락/중복이 없다.
3. 50~100페이지 검증으로 청크 크기, DPI, OCR 방식을 확정한다.
4. 300페이지 이상 POC를 같은 설정으로 최소 3회 실행해 메모리, OCR/평가 정확도, 시간을 보고한다.
5. 목표 장비 기준 임계값을 모두 만족할 때 실제 운용 적합으로 판정한다.
