# 설계 결정 이력

## D-001 — 검증 계층을 분리한다

* 상태: 확정
* 결정: 단위 테스트, 실제 PDF 통합 테스트, 대용량 POC를 분리한다.
* 이유: 작은 fixture는 빠르고 결정론적인 회귀 검증에 적합하지만, 300페이지 스캔 PDF의 메모리·OCR 품질·처리 시간은 실제 엔진과 장비가 필요한 POC에서만 입증할 수 있다.

## D-002 — 대용량 POC는 단계적으로 확장한다

* 상태: 확정
* 결정: 1~5 → 10~30 → 50~100 → 300페이지 이상 순으로 검증 범위를 늘린다.
* 이유: 작은 입력에서 기능 오류를 먼저 제거하고, 중간 규모에서 청크 및 OCR 병목을 조정한 뒤 비용이 큰 300페이지 POC를 수행한다.

## D-003 — OCR 및 LLM을 인터페이스로 격리한다

* 상태: 확정
* 결정: OCR·LLM은 ABC 기반 인터페이스와 교체 가능한 어댑터로 구현한다.
* 이유: 개발 중에는 Fake/일반 Python/Ollama를 사용하고, 이후 OpenVINO 또는 다른 엔진으로 교체할 수 있어야 한다.

## D-004 — B권 OCR은 ROI 방식과 전체 OCR을 비교한다

* 상태: 확정
* 결정: B권 증빙서류 판정은 상단 25% ROI OCR을 지원하고, POC에서 전체 OCR 대비 정확도와 시간을 측정한다.
* 이유: 증빙 제목이 상단에 배치되는 문서 구조를 활용해 처리 비용을 낮추되, 탐지 누락이 허용 범위 이내인지 검증해야 한다.

## D-005 — POC 결과를 회귀 테스트로 환원한다

* 상태: 확정
* 결정: POC에서 발견한 오류는 최소 재현 fixture와 단위 테스트로 추가한다.
* 이유: 실제 문서에서 한 번 확인된 결함이 이후 리팩터링 또는 엔진 교체에서 다시 발생하지 않게 한다.

## D-006 — POC 대시보드는 단일 통합 진입점을 유지한다

* 상태: 확정
* 결정: 대시보드 실행 진입점은 `test_dashboard/app_integrated.py` 하나로 유지하고, 공통 Job/경로 유틸리티는 `test_dashboard/server.py`에서 재사용한다.
* 이유: 기능별 임시 앱과 다중 포트가 누적되면 실행 대상과 결과 확인 경로가 분산되어 POC 검증을 재현하기 어려워진다.

## D-007 — Test 05 문서 평가는 페이지 단위 근거를 보존한다

* 상태: 확정
* 결정: Test 05는 선택 PDF와 사용자가 입력한 평가 기준을 페이지별 텍스트·토큰 윈도우로 모델에 전달한다. 각 모델 원문 인용은 300자 이하의 발췌로 제한하고 입력 페이지에서 다시 찾아 `citation_pages`로 저장한다. 전체 발췌가 PDF의 표식·줄바꿈 차이로 불일치하면, 20자 이상 줄 단위 발췌로 동일 페이지를 찾는다. 문서 점수는 윈도우 점수의 단순 평균으로 표시한다.
* 이유: 이전의 반복 생성 텍스트와 단일 예시 문장 평가는 실제 제안서 전체를 읽은 결과가 아니었다. 페이지 범위와 인용을 함께 저장하면 평가 범위와 근거를 검토할 수 있다. 긴 원문 한 문장은 JSON 응답을 잘라 실패시킬 수 있어, 검증 가능한 짧은 연속 발췌를 사용한다. OCR은 별도 엔진 단계이므로 텍스트가 없는 스캔 페이지를 실제로 평가한 것처럼 표시하지 않는다.

## D-008 — 대시보드 실패 실행도 결과 이력에 보존한다

* 상태: 확정
* 결정: 대시보드 작업이 실패하면 작업 ID, 상태, 종료 코드, 캡처한 표준 출력/오류를 `tests/results/dashboard_job_*.json`으로 저장한다.
* 이유: 성공 POC만 결과 파일을 쓰면 실패한 실행은 이력 화면에서 사라져 원인을 재현·검토할 수 없다.

## D-009 — Test 05는 OCR을 기본 입력으로 사용한다

* 상태: 확정
* 결정: 실제 문서 평가 Test 05의 기본 OCR 모드는 전체 페이지 PaddleOCR(`all`)이다. 텍스트 부족 페이지만 OCR하는 `fallback`, OCR을 사용하지 않는 `text`는 POC 비교용으로만 제공한다. 페이지별 텍스트 출처와 OCR 렌더링 배율을 결과에 저장한다.
* 이유: 실제 제안서는 스캔 페이지와 이미지형 표·도표가 혼합되므로 PDF 텍스트 레이어만으로는 평가 근거가 누락된다. 전체 OCR을 기본으로 해야 이미지 중심 페이지도 평가 범위에 포함된다.

## D-010 — 배점표가 점수를 산정하고 AI는 코멘트를 생성한다

* 상태: 확정
* 결정: Test 05는 사용자가 제공한 배점표 JSON의 `max_score`와 `required_keywords`로 항목별 점수를 규칙 계산한다. Gemma에는 규칙 계산 결과와 관련 원문을 전달해 점수를 변경하지 않는 심사 코멘트와 인용만 생성하게 한다.
* 이유: LLM 윈도우별 점수 평균은 재현 가능한 공식 배점이 아니며 실제 심사 기준을 충족하지 못한다. 점수의 출처를 배점표로 고정하고, AI는 검토 가능한 설명과 근거를 제공하는 보조 역할을 맡는다.

## D-011 — 체계규격은 표·표식 결합 방식으로 후보를 추출한다

* 상태: 확정
* 결정: 텍스트 RFP PDF의 체계규격은 PyMuPDF 표 탐지로 우선 추출하고, 표 구조가 불완전한 페이지에서는 `**`(필수)·`∙`(일반) 표식이 있는 텍스트 행을 보조 후보로 수집한다. 모든 결과는 페이지와 영역 좌표를 보존한다.
* 이유: 실제 PDF는 화면상 표여도 논리적 행·열 또는 헤더를 일관되게 저장하지 않는다. 두 경로를 결합하면 규격 행 누락을 줄일 수 있다.

## D-012 — 복합 규격은 자동 확정하지 않는다

* 상태: 확정
* 결정: 단일 수치 비교는 구조화하되, 다중 수치 축, 수량 곱셈, 괄호 구성, 표식 불명확 조건은 `review_required`로 표시한다.
* 이유: 체계규격의 필수·일반 판정은 감점과 불합격 후보에 직접 영향을 준다. 추출 단계에서 의미를 과도하게 단순화하지 않는다.

## D-013 — 체계규격 표식 fallback은 표 문맥 안에서만 적용한다

* 상태: 확정
* 결정: `**`·`∙` 표식만으로 체계규격을 추출하지 않는다. 독립된 `규격`/`요구사항` 열, 규격·수량 헤더 또는 이미 시작된 체계규격 표의 연속 페이지에서만 표식 fallback을 사용한다.
* 이유: 사업수행능력 등 일반 평가표에도 동일한 글머리표가 사용될 수 있어, 문맥 제한이 없으면 이를 체계규격으로 오인한다.

## D-014 — RFP 서술 규칙은 효과와 수치가 명시된 경우에만 구조화한다

* 상태: 확정
* 결정: 합격 기준, 불합격, 가점, 감점과 같이 효과와 수치가 명확한 문장만 자동으로 구조화한다. 각 규칙은 원문 페이지와 발췌를 보존한다.
* 이유: 규칙의 예외와 문맥을 임의로 추론하지 않고, 단일 평가위원이 근거를 확인할 수 있게 해야 한다.

## D-015 — Sidecar는 텍스트 부족 페이지만 로컬 OCR로 대체한다

* 상태: 확정
* 결정: Sidecar의 RFP 분석과 제안서 평가는 우선 PDF 텍스트 레이어를 읽고, 20자 미만인 페이지만 로컬 PaddleOCR로 렌더링·인식한다. 페이지별 원문 출처를 보존하며, OCR 표식 행은 체계규격 후보로만 사용한다.
* 이유: 텍스트형 PDF 처리 시간을 유지하면서 스캔 PDF를 평가 범위에서 제외하지 않는다. 표 셀 구조를 OCR만으로 확정하면 오판 위험이 있으므로 복원하지 못한 구조는 검토 대상으로 남긴다.

## D-016 — RFP 분석은 업로드 직후 실행하고 결과를 검토 화면에 표시한다

* 상태: 확정
* 결정: RFP 파일 등록 후 `rfp-analysis` API를 즉시 호출하고, 필수 서류·정량 평가·정성 평가 후보를 실제 추출 결과로 표시한다. 정적 예시 목록은 사용하지 않는다.
* 이유: 분석 API가 있어도 UI에서 호출하지 않으면 평가위원이 추출 결과를 검토·수정할 수 없고, 시스템이 RFP 기반으로 동작하는지 확인할 수 없다.

## D-017 — 필수 서류 후보는 명시적인 제출 의무가 있는 문서명으로 제한한다

* 상태: 확정
* 결정: 서류명 뒤에 제출·첨부·제시·구비 의무가 명시된 문장만 필수 서류 후보로 표시한다. 미제출 감점, 인증 대상 설명, ‘제출을 요구한’ 과거 서술, 표 헤더 및 문장 조각은 제외한다.
* 이유: 단어 끝이 인증서·확약서라고 해서 모두 업체가 제출해야 하는 서류는 아니다. 불필요한 후보가 많으면 평가위원의 검토 부담과 잘못된 평가 위험이 커진다.

## D-018 — B권 증빙 표가 있으면 첫 열을 필수 서류의 우선 근거로 사용한다

* 상태: 확정
* 결정: `Ⅱ. 증빙자료`가 시작된 `항목 | 작성방법` 표의 첫 열을 필수 서류명으로 추출한다. 같은 형식의 A권 작성기준 표는 제외하고, 해당 표를 찾을 수 없는 경우에만 본문 제출 의무 문장을 보조 후보로 사용한다.
* 이유: 수정본 RFP에서 B권 증빙 목록은 표로 명시돼 있으며, 표 기반 추출이 문장 단위 정규식보다 문서명 경계와 평가 범위를 정확히 보존한다.

## D-019 — 규칙 기반 판정은 AI 코멘트를 기다리지 않는다

* 상태: 확정
* 결정: 제안서 평가 완료 시점은 PDF/OCR 추출, 배점표 규칙 판정, 근거 페이지 생성까지로 한다. OpenVINO Gemma의 심사 코멘트는 평가위원이 요청할 때 별도 비동기 작업으로 생성한다.
* 이유: 점수 후보와 근거는 규칙으로 결정되며, 생성형 코멘트가 이를 지연시킬 필요가 없다. 긴 제안서에서 사용자가 빠르게 심의를 시작할 수 있다.

## D-020 — 동일 원본의 OCR 결과는 sidecar 수명 동안 재사용한다

* 상태: 확정
* 결정: 파일 경로·크기·수정시각 및 OCR 설정이 같은 문서는 최근 4건까지 메모리에 캐시한다. 원본이 변경되거나 sidecar가 재시작되면 다시 추출한다.
* 이유: 동일 제안서를 기준 수정 후 반복 평가하는 흐름에서 PDF 렌더링·OCR을 반복하는 비용을 줄이되, 원본 갱신 결과가 오래된 캐시에 가려지지 않게 한다.

## D-021 — 온디바이스 영속 데이터는 SQLite에 저장한다

* 상태: 확정
* 결정: 별도 DB 서버 없이 앱 PC의 SQLite 파일에 PDF 해시·경로, 페이지별 텍스트/OCR 결과, 규칙 평가 결과를 저장한다. PDF 원본과 대형 렌더 이미지는 DB에 복사하지 않는다.
* 이유: 앱 재시작·재평가 시 느린 OCR을 재실행하지 않고, 망분리 환경에서도 평가 근거와 이력을 유지할 수 있다. 원본 중복 보관을 피하면 저장 공간과 민감 문서 노출 범위를 줄일 수 있다.
