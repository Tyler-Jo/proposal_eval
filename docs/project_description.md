# 근거 기반 AI 평가 지원 시스템 프로젝트 명세

> 현재 문서는 대화를 통해 확정된 제품·평가 요구사항의 기준 문서다.  
> 시스템은 평가위원을 대체하지 않고, 제안요청서에서 평가 규칙을 추출한 뒤 제안서의 충족 여부·점수 후보·검토 근거를 제시한다.

## 1. 시스템 정의와 목적

본 프로젝트는 발주기관의 제안요청서와 입찰 업체의 제안서를 분석하는 **근거 기반 AI 평가 지원 시스템**이다.

* 제안요청서의 평가항목, 배점, 판정조건, 제출·증빙 요건을 구조화한다.
* 업체가 제출한 A권과 B권을 평가기준과 대조한다.
* 명확한 정량 조건은 재현 가능한 규칙으로 자동 판정한다.
* 정성적이거나 모호한 조건은 AI가 근거와 검토 의견을 제시해 평가위원의 심의를 지원한다.
* 모든 판정 후보를 제안요청서 및 제안서의 원문 페이지·영역과 연결한다.

## 2. 용어

* **제안요청서(RFP):** 사업 진행 부서가 입찰 참여 업체에 제안서의 제출 형태, 작성 기준, 평가 기준, 필수 요건 등을 안내하기 위해 작성한 문서
* **제안서:** 제안업체가 제안요청서에 따라 작성·제출하는 전체 자료
* **A권(기본제안서):** 사업 수행 방안, 기술·기능 제안, 추진 계획 등 제안 본문
* **B권(제안업체 소개 및 증빙자료):** 업체 현황, 참가 자격, 수행실적, 인력, 신용등급 등 소개 및 증빙자료
* **사업 진행 부서:** 사업을 발주하고 제안요청서를 작성하는 주체
* **제안업체:** 사업에 입찰하고 A권과 B권을 제출하는 회사
* **평가위원:** 시스템이 제시한 판정·점수·코멘트·근거를 검토하고 수정·확정하는 사용자

## 3. 입력 문서

* 사업별 제안요청서 PDF 1건
* 제안업체별 A권 PDF 1건
* 제안업체별 B권 PDF 1건
* 파일당 수백 페이지까지 고려한다.

제안요청서는 **텍스트 레이어가 포함된 PDF를 기본 입력**으로 한다.

1. 텍스트와 문자 위치정보를 우선 추출한다.
2. 문자·선·셀의 좌표를 이용해 표의 행과 열, 병합 셀, 페이지 간 연속 표를 복원한다.
3. 텍스트 레이어가 없거나 손상된 페이지와 이미지 영역에만 OCR을 보조적으로 적용한다.
4. 페이지별 추출 방식(`text`, `ocr`, `mixed`)과 원문 좌표를 기록한다.

## 4. 평가 범위

### 4.1 포함 범위

* 체계성능 및 규격평가
* 사업수행능력평가
* 입찰 참가 자격의 적격 여부 검토 지원
* 필수 제출서류 및 증빙의 존재·유효성·일치 여부
* 제안서 작성·제출 기준 준수 여부와 감점
* 블라인드 위반 여부
* 감점, 실격 및 불합격 조건
* 정성평가 코멘트와 근거 제시

### 4.2 제외 또는 분리 범위

* 가격평가는 현재 핵심 평가 범위에서 제외하며, 필요 시 별도 모듈로 분리한다.
* 법적 효력이 있는 참가 자격, 실격, 점수 종합 및 최종 합격 판정은 시스템의 목적과 범위에서 제외한다.

### 4.3 평가 유형 분류 원칙

상위 평가명 또는 A·B권만으로 정량·정성을 구분하지 않는다. 사업수행능력평가에도 정량, 정성, 상대평가, 조건부 등급평가가 혼재하므로 **세부평가항목과 판정 규칙 단위**로 유형을 분류한다.

## 5. 제안요청서에서 추출할 정보

* 평가 구분과 상·하위 평가항목
* 항목별 배점과 총점
* 평가 방법과 판정 조건
* 필수 제출서류 및 인정 가능한 증빙
* 참가 자격 조건
* 가점·감점·실격·불합격 조건과 적용 상한
* 제안서 분량, 페이지 부여 등 작성·제출 준수사항
* 블라인드 위반 조건
* 상대평가 등급 및 강제 배분 기준
* 점수 계산식과 예외 조건
* 각 조건의 제안요청서 원문, 페이지 및 영역 좌표
* 해석이 모호하거나 서로 충돌하는 조건

분량, 감점값 등 사업별 기준은 애플리케이션에 고정하지 않고 해당 제안요청서에서 추출한다.

## 6. 체계규격 데이터 모델

체계규격은 일반적으로 `항목번호 / 구분 / 규격 / 수량` 형태의 표로 제시된다. 한 행에서 다음 정보를 추출한다.

* 장비명
* 항목번호와 상위 분류
* 구분
* 요구규격 원문
* 필수·일반 구분
* 상위규격 가점 대상 여부
* 요구조건 유형
* 비교 연산자, 기준값 및 단위
* 요구 수량
* AND·OR 복합조건
* 관련 표준·지침
* 제안요청서 원문 페이지와 영역 좌표
* 추출 및 해석 신뢰도

체계규격에서 다음 표식을 인식한다.

* `**`: 필수항목
* `∙`: 일반항목
* `[상위규격 제안 시 가점]`: 상위규격 가점 대상

표식은 감점과 불합격을 가르는 중요 정보다. 표식이 누락되거나 불명확하면 AI가 임의로 추정하지 않고 `검토 필요`로 분류한다.

## 7. 정량평가 판정

### 7.1 자동 판정 대상

* 수치의 이상·초과·이하·미만
* 범위와 허용오차
* 수량 및 동일 수량 조건
* 특정 기능·프로토콜·표준의 포함 여부
* 금지 또는 제거 조건
* 제출서류의 존재 여부
* 제안서 분량 초과율
* 명시적인 산식과 배점표
* AND·OR로 연결된 복합조건

### 7.2 판정 상태

* 충족
* 미충족
* 상위규격 충족
* 확인 불가
* 제안 내용과 증빙 불일치
* 사람의 해석 필요

### 7.3 규격평가 규칙

현재 확인된 예시 RFP의 규칙은 다음과 같다. 실제 평가에서는 사업별 제안요청서에서 규칙과 값을 추출해 적용한다.

* 체계규격 필수항목 충족 시 기본점수 24점
* 필수항목 하나 이상 미충족 시 불합격 후보
* 일반항목 미충족 시 항목당 0.5점 감점 후보
* 가점 대상 항목에서 요구 규격보다 10% 이상 높은 규격을 제안하면 항목당 0.3점 가점 후보, 최대 6점
* 제안규격과 제조사 확인서·카탈로그 등 증빙이 불일치하거나 확인 불가능하면 미충족 규칙 적용 후보
* 비교도표의 모델명·수량 누락 및 필수 제품인증서 미제출은 불합격 후보

불합격이나 법적 효력이 있는 판정은 시스템이 확정하지 않고 평가위원에게 검토를 요청한다.

### 7.4 정량표 안의 정성 조건

`안정적 운용에 적합`, `통화품질에 지장을 주지 않음`, `연동 보장`처럼 수치 비교만으로 확정할 수 없는 조건은 체계규격 표 안에 있더라도 정성적 확인 항목으로 분류한다. AI는 관련 내용을 찾고 근거를 제시하되 평가위원이 판정한다.

## 8. 정성평가 코멘트와 등급 산정

### 8.1 코멘트 작성 단위와 형식

AI 코멘트는 상위 평가항목 전체가 아니라 실제 배점이 부여되는 최소 세부평가요소 단위로 작성한다. 각 코멘트는 다음 내용을 포함한다.

1. RFP 요구사항 요약
2. 제안서의 충족 내용
3. 미흡·누락 또는 확인 불가 내용
4. RFP에 명시된 등급 제한 조건의 적용 여부
5. AI 잠정 등급과 판단 이유
6. RFP 및 A·B권 원문 근거
7. 평가위원 확인사항

`미제안`은 단순 검색 실패와 구분한다. AI가 관련 내용을 찾지 못한 최초 상태는 `관련 내용 미발견`으로 표시하고 평가위원 확인 후 미제안으로 확정한다.

### 8.2 잠정 등급 산정

AI는 개별 업체의 요구요소 포함 여부, 구체성, 실행 가능성, A·B권 간 일관성, 증빙, 위험 대응 및 차별성을 분석해 **잠정 등급 후보**를 제시한다. RFP에 별도 평가요소가 있으면 해당 요소를 우선하며, 일반 분석 관점은 보조 기준으로만 사용한다.

* RFP에 명시된 미제안·누락·기준 미달에 따른 등급 상한 또는 최저등급 규칙을 먼저 적용한다.
* 등급 명칭, 점수 비율 및 환산식은 사업별 RFP에서 추출하며 애플리케이션에 고정하지 않는다.
* 잠정 등급과 환산점수에는 `AI 후보`임을 화면과 데이터에 명확히 표시한다.
* AI 잠정 등급은 평가위원이 검토·수정할 수 있으며 AI 원본과 위원 검토값을 별도 필드로 저장한다.

### 8.3 상대평가 비교 지원

상대평가 항목은 모든 제안업체의 동일 평가요소 분석이 끝난 뒤 업체 간 강점과 약점을 비교한다. RFP에 업체 수별 강제 배분표가 있으면 이를 적용해 등급 배정 후보를 생성한다.

* 비교 대상 업체가 부족하거나 분석이 완료되지 않으면 `상대평가 대기` 상태로 둔다.
* AI의 상대평가 결과는 심의 참고용 후보이며 공식 등급이나 최종 점수로 취급하지 않는다.
* 개별 업체의 잠정 등급, 상대평가 배정 후보, 평가위원 검토값을 서로 덮어쓰지 않고 모두 보존한다.

정성평가의 주요 상태는 `AI 잠정 평가 / 상대평가 대기 / 상대평가 후보 / 위원 검토 필요 / 검토 완료`로 구분한다.

## 9. 작성·제출 기준 감점

확인된 예시 기준은 다음과 같다. 수치와 구간은 사업별 제안요청서에서 추출한다.

* 제안서 분량 및 작성기준 미준수 전체 감점 상한: 3.5점
* A권 분량 초과 감점 상한: 1.5점
  * 10% 미만 초과: 0.5점
  * 20% 미만 초과: 1점
  * 20% 이상 초과: 1.5점
* A·B권 작성기준 미준수 감점 상한: 2점
  * 회사명 식별 표시: 0.5점
  * 불필요 표기: 0.5점
  * 페이지 부여방법 미준수 또는 오류: 0.5점
  * 제품공급사·모델번호 미기재: 0.5점

감점 결과는 `대상 권 → 위반 항목 → 실제 위반 내용 → 적용 기준 → 감점 후보 → 근거 페이지 → 검토 상태`로 제공한다.

## 10. AI 권한과 불확실성 처리

* 명확한 수치, 포함, 수량, 제출 여부 조건은 규칙 엔진이 자동 판정한다.
* AI는 추출·구조화, 관련 근거 탐색, 정성 코멘트 및 검토 필요성 판단을 지원한다.
* AI가 배점표와 계산식을 임의로 변경하거나 근거 없이 점수를 생성하지 않는다.
* 표 병합, 페이지 연결, 기호, 수치, 단위 또는 복합조건 해석이 불확실하면 자동 확정하지 않는다.
* 특히 필수·일반 구분과 불합격 조건이 불확실하면 반드시 평가위원 검토 대상으로 올린다.

추출·판정 신뢰도는 `높음 / 중간 / 낮음 / 검토 필요`로 표시한다.

## 11. 근거 제시 요구사항

각 결과는 최소한 다음 정보를 포함한다.

* 적용한 RFP 평가항목과 규칙
* RFP 원문 발췌, 페이지 및 영역
* A권 또는 B권의 판정 대상 원문 발췌, 페이지 및 영역
* 사용한 증빙 문서와 일치 여부
* 계산 과정과 점수·감점·가점 후보
* 추출·판정 신뢰도
* 평가위원 검토가 필요한 이유

UI에서는 결과에서 해당 원문 위치로 이동해 전후 문맥과 표를 직접 확인할 수 있어야 한다.

## 12. 단일 평가위원 검토 절차와 변경 이력

시스템의 사용자는 단일 평가위원으로 한다. 평가위원은 `AI 잠정 평가 → 근거 검토 → 판정·등급·코멘트 수정 → 항목 검토 완료 → 검토 누락 확인 → 심의 지원자료 저장·내보내기` 순서로 사용한다.

* 필수항목 미충족, 실격·불합격, 참가 자격 미달, 증빙 불일치, 블라인드 위반, 등급 제한 및 낮은 신뢰도의 결과는 필수 검토 대상으로 표시한다.
* 평가위원은 판정, 등급, 코멘트 및 연결 근거를 수정할 수 있다.
* 판정이나 등급이 변경되면 RFP 산식으로 점수를 다시 계산한다. 예외적인 수동 점수는 별도 값으로 구분한다.
* **수정 사유 입력은 선택사항**으로 두며, 입력하지 않아도 저장·검토 완료를 차단하지 않는다.
* 상대평가 항목은 모든 업체의 분석이 끝난 뒤 비교·강제 배분 기준을 참고할 수 있게 한다.
* 미검토 항목, 필수 검토 대상, 배점 합계, 가감점 상한 및 강제 배분 오류는 경고하지만 공식 결과 확정 기능을 수행하지 않는다.
* 평가위원은 원하는 시점의 검토 내용을 심의 지원자료 스냅샷으로 저장·내보낼 수 있으며, 이후 수정 시 기존 스냅샷을 보존한다.

온디바이스 환경에서도 변경 이력을 보존한다. 별도 서버 대신 애플리케이션 전용 로컬 SQLite 데이터베이스에 다음 이벤트를 추가 방식으로 기록한다.

* AI 최초 판정 생성
* 평가위원의 판정·등급·점수·코멘트·근거 변경
* 항목 검토 완료 및 재검토
* 상대평가 후보와 평가위원 검토값 변경
* 심의 지원자료 스냅샷 생성 및 재검토

이력에는 사업·업체·평가항목 식별자, 작업 유형, 변경 전·후 값, 선택 입력된 수정 사유, 단일 로컬 사용자 식별자, 장치 시각 및 평가 규칙 버전을 포함한다. 원문 PDF 전체를 이벤트마다 복제하지 않고 문서 식별자, 페이지, 영역 좌표와 필요한 발췌만 참조한다.

로컬 이력은 네트워크 없이 생성·조회·내보내기가 가능해야 하며, 데이터베이스와 결과 패키지를 백업·복원할 수 있어야 한다. 단일 장치의 관리자 권한을 가진 사용자가 파일 자체를 조작하는 것까지 완전히 방지할 수는 없으므로, 필요하면 후속 단계에서 이벤트 해시 연결과 서명된 내보내기로 변조 탐지 수준을 강화한다.

## 13. 구현 및 운용 제약

최종 시스템은 인터넷이 차단된 환경에서 동작하는 Tauri UI와 Python sidecar 기반 데스크톱 애플리케이션을 목표로 한다. 실제 운용 장비는 Intel Core Ultra 계열 NPU 랩탑을 고려한다.

OCR과 LLM은 교체 가능한 인터페이스로 격리한다. 점수 계산은 구조화된 평가 규칙이 담당하고, LLM은 규칙을 변경하지 않는 범위에서 추출, 비교, 코멘트 및 근거 제시를 지원한다.

## 14. 개발·빌드·배포 운영 환경

개발 환경과 최종 운용 환경을 다음과 같이 분리한다.

* 개발은 Linux 환경에서 수행한다.
* Windows용 설치 패키지의 빌드는 Windows 빌드 전용 랩탑에서 수행한다.
* 빌드가 완료된 설치 패키지는 USB 등 오프라인 매체로 다른 Windows 운용 랩탑으로 옮겨 설치·사용한다.
* 운용 랩탑은 인터넷 연결, Python, Node.js, Rust, `uv`를 별도로 설치하지 않아도 되어야 한다.

### 14.1 Windows 빌드 랩탑

Windows 빌드 랩탑에는 Windows용 Tauri/Rust 빌드 환경과 패키징에 사용할 Node.js, MSVC C++ Build Tools를 준비한다. 이 장비에서 Windows용 Python sidecar와 해당 네이티브 의존성을 구성하고, Tauri 설치 패키지(`.msi` 또는 `.exe`)를 생성한다. Linux 개발 환경에서 생성한 Windows 설치 패키지를 전제로 하지 않는다.

### 14.2 설치 패키지의 포함물

설치 패키지는 최종 사용에 필요한 실행 구성요소를 함께 포함해야 한다.

* Tauri 데스크톱 앱
* Windows용 Python 런타임 및 Python sidecar
* PDF 처리, SQLite, OCR에 필요한 Python 패키지와 네이티브 라이브러리
* 로컬 PaddleOCR 탐지·한글 인식 모델
* 선택 기능인 AI 심사 코멘트에 필요한 OpenVINO 런타임과 변환된 로컬 LLM 모델

OCR과 LLM 모델은 빌드 과정에서 자동 생성되는 산출물이 아니다. 검증된 모델 파일을 빌드 입력으로 관리하고 설치 패키지에 복사해야 한다. LLM 모델을 포함하지 않는 배포본은 규칙 기반 평가와 OCR을 제공하며, AI 심사 코멘트는 명시적으로 사용할 수 없거나 규칙 기반 설명으로 표시한다.

### 14.3 운용 랩탑과 데이터

운용 랩탑은 설치 패키지와 WebView2 Runtime만으로 실행 가능해야 한다. WebView2 Runtime이 없는 환경에서는 설치 과정에서 함께 설치하거나 설치 전 확인한다. 평가 데이터와 OCR 캐시는 기본적으로 `%LOCALAPPDATA%\\AVISCheck`의 로컬 SQLite에 저장하며, 원본 PDF는 복사하지 않고 사용자가 선택한 위치를 참조한다. 따라서 PDF 원본을 이동·삭제하면 이전 결과에서 해당 원문을 다시 열 수 없음을 사용자에게 안내한다.

### 14.4 배포 검증

릴리스 전에는 빌드 랩탑과 분리된 깨끗한 Windows 운용 랩탑에서 네트워크 없이 설치·실행·텍스트 PDF 평가·스캔 PDF OCR·결과 재열기를 검증한다. LLM 포함 배포본은 AI 심사 코멘트 생성까지 검증하며, 미포함 배포본은 해당 기능의 제한과 규칙 기반 fallback 표시를 검증한다.
