## 1. 프로젝트 목적

이 프로젝트는 인터넷이 차단된 환경의 Intel NPU 노트북에서 RFP, A권 제안서, B권 증빙자료를 평가하고, 과거 제안요청서를 기반으로 신규 추진사업의 제안요청서 초안을 생성하는 데스크톱 애
플리케이션의 Python Sidecar 핵심 로직을 구현한다.

주요 기능은 다음과 같다.

* B권 정량 평가: 필수 증빙서류 확인, 블라인드 위반 및 감점 요소 탐지
* A권 정성 평가: RFP 대비 제안 내용 분석, Chat-RAG, 페이지/섹션 근거 인용
* 컴플라이언스: 법령 및 발주처 금지 조항 위반 탐지
* 제안요청서 생성: 과거 제안요청서를 분석해 신규 추진사업의 제안요청서 초안을 생성하고, 생성 근거와 검토 필요 항목을 제공

## 2. 현재 개발 범위

현재는 Tauri UI, 배포용 OpenVINO 최적화, 실제 `.exe` 패키징을 구현하지 않는다. Python 핵심 로직, 엔진 인터페이스, 단위 테스트, 실제 스캔 PDF 기반 단계적 POC를 우선한다.

## 3. 작업 시작 전 필수 문서

작업 전 아래 문서를 순서대로 읽는다.

1. `docs/current_state.md` — 현재 우선순위와 블로커
2. `docs/project_description.md` — 제품 및 모듈 요구사항
3. `docs/unit_test_poc_plan.md` — 단위 테스트부터 300페이지 POC까지의 검증 계획

테스트 관련 구현 작업은 추가로 `docs/workflows/implement_test.md`를 읽는다.

## 4. 설계 원칙

* OCR 및 LLM은 ABC 기반 인터페이스 뒤에 둔다. 구체 엔진은 교체 가능해야 한다.
* 페이지 기반 데이터는 페이지 번호와 근거 위치를 보존한다.
* 제안요청서 생성 결과는 원본 과거 제안요청서의 근거 페이지/섹션을 보존하고, 사실·일정·예산·법적 요건 등 확정이 필요한 내용은 초안 또는 검토 필요 상태로 명시한다.
* 테스트용 OCR/LLM은 Fake 구현체로 대체 가능해야 한다.
* 단위 테스트는 네트워크, 실제 Ollama, 실제 대용량 PDF에 의존하지 않고 반복 가능해야 한다.
* 실제 OCR 및 대용량 문서 검증은 `integration`/`poc`으로 단위 테스트와 분리한다.
* POC 실패는 최소 재현 fixture로 축소해 단위 테스트에 추가한다.
* 실제 제안서·RFP·개인정보가 들어간 원본 문서는 저장소에 커밋하지 않는다.

## 5. 테스트 및 POC 규칙

검증은 다음 순서로 확장한다.

1. 1~5페이지 fixture 단위 테스트
2. 10~30페이지 실제 스캔 PDF 통합 테스트
3. 50~100페이지 확장 검증
4. 300페이지 이상 실제 운용 POC

300페이지 POC에서는 최소 30/50페이지 청크를 비교하고, 설정별 3회 이상 실행한다. 페이지 누락/중복, RSS·최대 RSS·GC 후 RSS, 단계별 처리 시간, OCR 정확도, 탐지 Precision/Recall/F1, 인용
페이지 정확도를 기록한다.

## 6. 작업 완료 기준

* 요구사항, 구현, 테스트가 서로 일치한다.
* 단위 테스트는 기본 `pytest`에서 빠르게 실행된다.
* 외부 엔진 또는 큰 PDF가 필요한 테스트는 명시적 marker/명령으로 분리한다.
* 구현 또는 검증이 끝나면 `docs/current_state.md`에 완료 항목, 다음 작업, 블로커를 갱신한다.
* 새로운 설계 선택은 이유와 함께 `docs/decision_log.md`에 기록한다.
