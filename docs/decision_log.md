# 설계 결정 이력

## D-001 — 검증 계층을 분리한다

* 상태: 확정
* 결정: 단위 테스트, 실제 PDF 통합 테스트, 대용량 POC를 분리한다.
* 이유: 작은 fixture는 빠르고 결정론적인 회귀 검증에 적합하지만, 300페이지 스캔 PDF의 메모리·OCR 품질·처리 시간은 실제 엔진과 장비가 필요한 POC에서만 입증할 수 있다.

## D-002 — 대용량 POC는 단계적으로 확장한다

* 상태: 확정
* 결정: 1~5 → 10~30 → 50~100 → 300페이지 이상 순으로 검증 범위를 늘린다.
* 이유: 작은 입력에서 기능 오류를 먼저 제거하고, 중간 규모에서 청크 및 OCR 병목을 조정한 뒤 비용이 큰 300페이지 POC를 수행한다.

## D-003 — OCR 및 LLM을 인터페이스로 격리한다

* 상태: 확정
* 결정: OCR·LLM은 ABC 기반 인터페이스와 교체 가능한 어댑터로 구현한다.
* 이유: 개발 중에는 Fake/일반 Python/Ollama를 사용하고, 이후 OpenVINO 또는 다른 엔진으로 교체할 수 있어야 한다.

## D-004 — B권 OCR은 ROI 방식과 전체 OCR을 비교한다

* 상태: 확정
* 결정: B권 증빙서류 판정은 상단 25% ROI OCR을 지원하고, POC에서 전체 OCR 대비 정확도와 시간을 측정한다.
* 이유: 증빙 제목이 상단에 배치되는 문서 구조를 활용해 처리 비용을 낮추되, 탐지 누락이 허용 범위 이내인지 검증해야 한다.

## D-005 — POC 결과를 회귀 테스트로 환원한다

* 상태: 확정
* 결정: POC에서 발견한 오류는 최소 재현 fixture와 단위 테스트로 추가한다.
* 이유: 실제 문서에서 한 번 확인된 결함이 이후 리팩터링 또는 엔진 교체에서 다시 발생하지 않게 한다.

## D-006 — POC 대시보드는 단일 통합 진입점을 유지한다

* 상태: 확정
* 결정: 대시보드 실행 진입점은 `test_dashboard/app_integrated.py` 하나로 유지하고, 공통 Job/경로 유틸리티는 `test_dashboard/server.py`에서 재사용한다.
* 이유: 기능별 임시 앱과 다중 포트가 누적되면 실행 대상과 결과 확인 경로가 분산되어 POC 검증을 재현하기 어려워진다.

## D-007 — Test 05 문서 평가는 페이지 단위 근거를 보존한다

* 상태: 확정
* 결정: Test 05는 선택 PDF와 사용자가 입력한 평가 기준을 페이지별 텍스트·토큰 윈도우로 모델에 전달한다. 각 모델 원문 인용은 300자 이하의 발췌로 제한하고 입력 페이지에서 다시 찾아 `citation_pages`로 저장한다. 전체 발췌가 PDF의 표식·줄바꿈 차이로 불일치하면, 20자 이상 줄 단위 발췌로 동일 페이지를 찾는다. 문서 점수는 윈도우 점수의 단순 평균으로 표시한다.
* 이유: 이전의 반복 생성 텍스트와 단일 예시 문장 평가는 실제 제안서 전체를 읽은 결과가 아니었다. 페이지 범위와 인용을 함께 저장하면 평가 범위와 근거를 검토할 수 있다. 긴 원문 한 문장은 JSON 응답을 잘라 실패시킬 수 있어, 검증 가능한 짧은 연속 발췌를 사용한다. OCR은 별도 엔진 단계이므로 텍스트가 없는 스캔 페이지를 실제로 평가한 것처럼 표시하지 않는다.

## D-008 — 대시보드 실패 실행도 결과 이력에 보존한다

* 상태: 확정
* 결정: 대시보드 작업이 실패하면 작업 ID, 상태, 종료 코드, 캡처한 표준 출력/오류를 `tests/results/dashboard_job_*.json`으로 저장한다.
* 이유: 성공 POC만 결과 파일을 쓰면 실패한 실행은 이력 화면에서 사라져 원인을 재현·검토할 수 없다.

## D-009 — Test 05는 OCR을 기본 입력으로 사용한다

* 상태: 대체됨(D-014)
* 결정: 실제 문서 평가 Test 05의 기본 OCR 모드는 전체 페이지 PaddleOCR(`all`)이다. 텍스트 부족 페이지만 OCR하는 `fallback`, OCR을 사용하지 않는 `text`는 POC 비교용으로만 제공한다. 페이지별 텍스트 출처와 OCR 렌더링 배율을 결과에 저장한다.
* 이유: 실제 제안서는 스캔 페이지와 이미지형 표·도표가 혼합되므로 PDF 텍스트 레이어만으로는 평가 근거가 누락된다. 전체 OCR을 기본으로 해야 이미지 중심 페이지도 평가 범위에 포함된다.
* 대체 사유: 제안요청서는 텍스트 레이어 PDF일 가능성이 높다는 입력 가정을 확정하여, 전체 OCR 대신 텍스트·좌표 추출을 우선하고 필요한 페이지와 영역에만 OCR을 적용한다.

## D-010 — 배점표가 점수를 산정하고 AI는 코멘트를 생성한다

* 상태: 확정
* 결정: Test 05는 사용자가 제공한 배점표 JSON의 `max_score`와 `required_keywords`로 항목별 점수를 규칙 계산한다. Gemma에는 규칙 계산 결과와 관련 원문을 전달해 점수를 변경하지 않는 심사 코멘트와 인용만 생성하게 한다.
* 이유: LLM 윈도우별 점수 평균은 재현 가능한 공식 배점이 아니며 실제 심사 기준을 충족하지 못한다. 점수의 출처를 배점표로 고정하고, AI는 검토 가능한 설명과 근거를 제공하는 보조 역할을 맡는다.

## D-011 — 제품을 근거 기반 AI 평가 지원 시스템으로 정의한다

* 상태: 일부 대체됨(D-019)
* 결정: 시스템은 평가위원을 대체하지 않는다. 제안요청서의 평가 규칙을 구조화하고, 제안서의 판정·점수·코멘트 후보와 양쪽 문서의 원문 근거를 제공하며 평가위원이 최종 확정한다.
* 이유: 불합격, 참가 자격 및 정성적 판단에는 문맥 해석과 책임 있는 사람의 검토가 필요하다.

## D-012 — A권과 B권의 용어 및 역할을 고정한다

* 상태: 확정
* 결정: A권은 기본제안서, B권은 제안업체 소개 및 증빙자료로 정의한다. 정량·정성 여부를 권 구분만으로 결정하지 않고 세부평가항목과 판정 규칙 단위로 분류한다.
* 이유: 사업수행능력평가에는 수행실적·재무구조 같은 정량항목과 사업이해도·추진전략 같은 정성·상대평가 항목이 함께 존재한다.

## D-013 — 가격평가를 핵심 범위에서 분리한다

* 상태: 확정
* 결정: 규격평가, 사업수행능력평가, 참가 자격 검토, 제출·증빙, 작성기준, 블라인드, 감점 및 실격 조건은 포함한다. 가격평가는 현재 핵심 범위에서 제외하고 필요 시 별도 모듈로 구성한다.
* 이유: 가격평가는 기술·사업수행능력 및 문서 준수 평가와 계산 근거와 절차가 다르므로 독립적으로 확장하는 편이 적절하다.

## D-014 — 텍스트 PDF를 우선하고 OCR은 보조적으로 사용한다

* 상태: 확정
* 결정: 제안요청서의 기본 입력은 텍스트 레이어 PDF로 한다. 텍스트와 문자 좌표로 표를 복원하고, 텍스트가 없거나 손상된 페이지와 이미지 영역에 OCR을 적용한다.
* 이유: 텍스트 PDF는 OCR보다 정확한 문자와 위치정보를 제공하지만, 화면상의 표가 논리적 행·열로 저장되지 않을 수 있으므로 좌표 기반 표 복원은 여전히 필요하다.

## D-015 — 필수·일반 표식을 중요 판정 속성으로 취급한다

* 상태: 확정
* 결정: 체계규격의 `**`는 필수항목, `∙`는 일반항목, `[상위규격 제안 시 가점]`은 가점 대상으로 추출한다. 표식이 불명확하면 추정하지 않고 평가위원 검토 대상으로 분류한다.
* 이유: 동일한 미충족도 필수항목이면 불합격, 일반항목이면 감점으로 이어질 수 있어 표식 오류의 영향이 크다.

## D-016 — 명확한 정량 조건만 자동 판정한다

* 상태: 확정
* 결정: 수치, 포함, 수량, 제출 여부 및 명시적 산식은 규칙으로 자동 판정한다. 모호한 조건, 증빙 불일치, 필수항목 미충족과 같이 영향이 큰 결과는 근거와 함께 검토 요청하며 평가위원의 심의 판단을 지원한다.
* 이유: 자동화의 재현성을 확보하면서도 문서 해석 오류가 감점·불합격으로 곧바로 확정되는 것을 방지해야 한다.

## D-017 — AI가 정성평가 잠정 등급을 명확히 구분해 제시한다

* 상태: 일부 대체됨(D-019)
* 결정: AI는 개별 업체의 세부평가요소별 근거 기반 코멘트와 잠정 등급 후보를 제시한다. 화면과 데이터에서 이를 `AI 후보`로 표시하고, 상대평가 후보 및 평가위원이 확정한 최종 등급·점수와 별도로 저장한다.
* 이유: 잠정 등급은 평가위원의 판단 속도를 높일 수 있지만, 모든 업체 비교와 강제 배분 전에는 상대평가의 최종 등급이 될 수 없으며 AI 판단을 최종 판정으로 오인해서는 안 된다.

## D-018 — 수정 사유는 선택사항으로 두고 변경 이력은 로컬에 보존한다

* 상태: 확정
* 결정: 평가위원이 AI 결과를 수정할 때 수정 사유 입력은 선택사항으로 둔다. 판정·등급·점수·코멘트·근거의 변경 전후 값과 확정 이벤트는 애플리케이션 전용 로컬 SQLite 데이터베이스에 추가 방식으로 저장한다.
* 이유: 사유 입력을 강제하지 않아 평가 흐름의 부담을 낮추면서도, 온디바이스 환경에서 서버 없이 변경 과정과 결과 버전을 재현할 수 있어야 한다.
* 한계: 로컬 관리자에 의한 데이터베이스 파일 조작을 완전히 차단할 수는 없다. 높은 변조 방지 수준이 필요하면 이벤트 해시 연결, 내보내기 서명 및 외부 보관 정책을 별도로 적용한다.

## D-019 — 단일 평가위원의 심의 지원에 집중한다

* 상태: 확정
* 결정: 시스템 사용자는 단일 평가위원으로 하며, AI의 판정·잠정 등급·비교·근거를 검토하고 수정하는 심의 지원 흐름을 제공한다. 점수를 종합해 공식 결과나 최종 합격을 확정하는 기능은 제품 목적에서 제외한다.
* 이유: 제품의 핵심 가치는 평가 결과의 의사결정 자동화가 아니라, 평가위원이 제안서와 RFP의 근거를 빠르고 일관되게 확인하도록 지원하는 데 있다.
* 영향: `최종 확정` 대신 `검토 완료`와 `심의 지원자료 스냅샷`을 사용하고, AI 후보·위원 검토값·변경 이력을 보존한다.
